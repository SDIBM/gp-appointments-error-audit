The screens today, and the obstacles users face

What the audit found across the screens, and what users can run into from checking an appointment to booking or cancelling it.

The screens today

Inconsistent

  • Titles: the same kind of fault shows "Cannot show appointments", "Cannot show GP appointments", "Cannot access GP appointments" or "The service is unavailable".
  • Content: wording, order and links differ. "Try again" appears on some screens and not others.

Duplicated

  • Same screen, different causes: 500, 502 and 504 share one screen, and 409 and 461 share the cancel screen.
  • Several screens, same cause: 403 has two screens, and 401 has two versions.

Errors that are not errors

  • No slots, 403, 409, 460 and 461 are expected outcomes, but some are presented as errors.

Signposting gaps

  • Few screens point to another route such as an online consultation or "Ask your GP".
  • Users need to find their GP surgery's contact details, and many of these screens do not help them. The 403 cancel screen gives no way to contact the surgery.

Not reaching the right screen

  • 400 and 599 often show the generic "service is unavailable" screen, and 400 offers "Try again", which cannot help.

Unclear outcome

  • After a failed booking or cancellation, users are not told whether it went through.

Obstacles users can face, from start to finish

1 Check appointments

  • No appointments available (200 + zero slots)
  • Online booking switched off by the practice (403)
  • GP session cannot be set up (598, 599)
  • GP system slow or failing (500, 502, 504)

2 Book

  • Slot taken by someone else (409)
  • Booking limit reached (460)
  • Booking fails (400, 500, 502, 504), and the user may not know if it went through

3 Cancel

  • Too late to cancel (461)
  • Already cancelled or passed (409)
  • Practice has disabled cancelling (403)
  • Cancellation fails (500, 502, 504)

Any step

  • Signed out after inactivity (401)
  • Patient ID not recognised, TPP (467)

Several clicks, several requests

Each Try again, refresh or return to the start sends a new request, and each is counted.

Is it cached?

The app saves the slots for the booking flow. The backend does not cache: every request goes to the GP system, so slots are always live.

How IM1 works

The app talks to the GP system (EMIS or TPP) live, through its backend. No copy of appointments is held. A GP session is needed first (598).

What this means for the counts Counts are requests, not users. One booking journey can send several slot requests but only one booking request.

The guideline each screen is checked against

Each code slide ends with how that screen should be, based on the NHS App design system error screen pattern.

How an error screen is structured

  1. Heading: starts "There is a problem" plus the feature that has gone wrong.
  2. Body text: concise; how to resolve it, or more detail.
  3. Button: a secondary button for an action that may help (Try again, Log out). Straight after the related text.
  4. Other options: always say how to finish the task another way, often contacting the GP surgery. Use secondary card links for other NHS App services.
  5. Urgent help: "For urgent medical advice. Use 111 online or call 111."
  6. Technical support: "For technical support. Make a note of the error code xxxxx and then contact the NHS App team."

Try again

  • Only when the problem is temporary and a retry is likely to work straight away.
  • Otherwise do not show it. "Try again later" can go in the text.
  • Users can select it once. If it fails, a follow-on screen says "There is still a problem …" and gives other ways to finish.

Do not

  • blame the user, or use exclamation marks or "oops"
  • add a back link or breadcrumbs at the top
  • use jargon such as "500", "504", "bad request"
  • use red text to warn people
  • offer too many links
  • show the app header or footer to a logged-out user
Scope of the guideline The pattern is for unexpected problems. Negative endpoints are expected outcomes, so their screens apply the same principles: say what has happened, what to do next, give another way to finish, and signpost 111. GDS adds that, if a user is part way through a transaction, the page should say what has happened to their answers.

Sources: NHS App design system: Error screens · GOV.UK Design System: There is a problem with the service pages

Reading the numbers

Every request in the 30 days is counted, not a sample.

What the counts are

  • A count is the number of requests that returned a code, not the number of people.
  • One user can send several requests, so counts are higher than user numbers.

Volume bands used in this deck

Very high 100,000 or more · High 10,000 to 99,999 · Medium 1,000 to 9,999 · Low 50 to 999 · Very low fewer than 50.

Very low volume means the code is real but too rare to compare.
